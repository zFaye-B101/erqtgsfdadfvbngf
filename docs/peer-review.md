# 互评与替代方案

团队于 2026-10-11 增加的协作约定，适用于成员和 AI 对他人更新的评价。目标是发现实际问题、交流不同方法，保持可复现和明确的责任边界；不是要求否定原方案，也不是新增课程评分标准。

## 何时评审

- 每次接手开发，先看本轮将使用/修改的模块有哪些新提交，以及是否有尚未处理的相关评审。按需对这些改动做增量检查，不要求每次全仓库审计。
- 数据划分、特征、模型、公共接口或评估流程出现实质更新时，适合交给另一位成员或其 AI 做交叉评审。作者的自查有价值，但不能冒称独立互评；同一 AI 的再次检查也不能冒称另一名成员认可。
- 维持直接提交 `main`，不设置强制 PR 或“每次提交都要等别人批准”的门槛。严重问题应明确标记为影响正式实验/提交，协调修复后再使用受影响结果。
- 本流程不启动定时监控、不自动向其他会话发消息，也不允许读取无关私人文件。只在获准的当前仓库工作范围内执行。

## 评审依据与内容

1. **固定版本和范围。** 记录被评审提交 SHA、文件和函数；Notebook 使用单元格 ID（若存在）、标题和关键代码定位，不使用可能漂移的执行编号。区分提交内容与未提交草稿。
2. **先理解再评价。** 阅读当前任务要求、方案、相关源码及调用方，不只看 README 或代码表面。检查已有记录，避免重复报告已经修复的问题；旧问题在新提交中仍存在时补充复查证据。
3. **问题分级。** 确认问题写明触发条件、影响与证据；尚未复现的疑点标为待验证；性能、风格或结构上的其他做法标为可选改进。结果中先列高风险问题，再列建议。无问题可以明确写“在本次范围内未发现问题”，同时列出未覆盖测试。
4. **重点检查。** 课程要求与研究问题是否匹配，商品级隔离与数据泄漏，训练/验证/测试边界，指标和阈值实现，形状/标签/路径接口，随机性和可复现性，内存/时间成本，英文提交代码规范及已有中文副本同步情况。
5. **提出替代方案。** 对值得更改的点给出可实施的小修复或其他方法，并说明与现状相比改善什么、失去什么。通常比较现状和一至两个有价值的方案即可，不强制凑数量。区分预期收益与实测收益，不能凭算法更新就声称分数更高或运行更快。
6. **验证成本适度。** 写明检查是静态阅读、合成测试、真实小样本还是完整实验，记录命令、环境和实际输出摘要。不要为互评擅自安装依赖、联网下载、租算力或运行昂贵全量训练；需要这些操作时先取得相应授权。

## 记录与回应

- 真实评审保存为 `docs/reviews/YYYY-MM-DD_<short-sha>_<scope>_<reviewer>.md`。首次真实评审时再创建该目录；用不同文件避免多人同时修改一条记录。reviewer 使用已知姓名/标识或诚实标注“本会话 AI”，不编造组员身份。
- 记录是仓库文档，可中文编写；不能将其中的中文直接混进英文提交代码。每次保存/更新记录仍同步 README 的简短摘要和受影响文件，不把全文堆进 README。
- 每条发现给予稳定编号，例如 `R1`。负责人逐条回应：采纳、暂缓或不采纳，并说明原因。未获回应时明确待回应，不能由评审者代替对方表示同意。
- 建议状态为 `待回应`；确认采纳后为 `待实施`；修改提交后为 `待验证`；对新提交复测通过后为 `已验证`。还可标记 `暂缓` 或 `不采纳` 并保留理由。新版本改变前提时标记 `已过期/需复查`，不能直接算修复。
- 默认只评价，不修改被评审的实现。需要修改他人负责的文件时先协调；数据划分、研究问题、算法、指标和正式实验协议的调整须用户确认。随后由明确的实施者进行小范围改动，保留其他人的工作。
- 采用方案后同步调用方、测试、运行文档和已有中文学习副本；记录实施提交及验证证据。没有验证不要把状态写成通过，也不要因为分歧就反复互相覆盖代码。
- 评审记录默认属于开发协作文档，不自动进入最终代码 ZIP；实际提交所需会议记录依官方要求单独整理。

以下只是模板，不表示已有评审结论。

```markdown
# <范围>互评

- 被评审提交：<完整 SHA>
- 评审者：<真实身份或本会话 AI>
- 日期：<YYYY-MM-DD>
- 文件与范围：<路径、函数/行号或单元格 ID/标题>
- 依据：<要求、当前方案、相关调用方>
- 验证方式：<静态阅读/实际运行的命令、环境与数据范围>
- 未覆盖：<未运行测试与剩余风险>

## R1：<具体问题或改进点>

- 类型/优先级：<确认问题/待验证风险/可选改进；影响程度>
- 状态：待回应
- 位置与触发条件：<可定位、可复查>
- 证据和影响：<实际观察；推测明确标注>
- 保留现状：<优点与限制>
- 方案 A：<最小调整、收益、代价、接口/结果影响>
- 方案 B（有价值时）：<其他方法及取舍>
- 建议与验证方法：<为何推荐；如何检验>
- 负责人回应：待回应
- 实施者/提交：尚未实施
- 复查结果：尚未验证

## 结论

- <建议优先处理的事项，或本范围未发现问题>
- <是否影响后续实验；剩余测试缺口>
```

纯粹没有发现问题的评审不需要虚构 `R1`；保留范围、验证、缺口与结论即可。
